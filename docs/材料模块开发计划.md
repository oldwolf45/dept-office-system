## 1. 总纲与开发纪律（对照复盘修正）

复盘给办公系统挑的 6 项实质问题，材料模块重写必须逐项落实，不再犯：

| 复盘问题 | 本计划落地方式 |
|---|---|
| #1 测试时机后置 | **任务级测试先行**：每个任务动手前先写 vitest + supertest 用例（接口 / 规则），写完即跑；阶段末跑全量做验收 |
| #2 调试空白 | 缺陷强制走四步：复现 → 最小化 → 追根因 → 修复并防回归；报错位置 ≠ 问题位置 |
| #3 无代码评审 | 每任务交付前过 10 条评审检查单（命名 / 组件超长 / any 违规 / 软删除落实 / 接口走 api 层 / 权限前端不渲染+后端拒绝 / 魔法数字 / 错误码统一 / 日志 / 无硬编码路径） |
| #4 无 Git 分支 | 并入办公系统仓库；分支 `feature/material-module`，禁止直改主分支，完工合并打标签 v1.1 |
| #5 验收标准双重化 | 标准唯一源 = PRD §10；验收 agent 只执行核对，无权制定 / 改标准，改标准走 PRD 升版 |
| #6 经验未沉淀 | 每阶段一份开发契约（模板见第 6 部分），契约 / 评审单 / 验收单模板化进办公系统开发规范 |

**顺序原则（复盘 §6 修正）**：先依赖后优先级；无依赖的同层内 P0 先于 P1；贯穿项（鉴权中间件、软删除、统一响应、操作日志）不占阶段位，作为 T0 基础件提前铺好。

**纪律红线**：禁止删测试、跳测、降标准过关；任何一端发现契约与 PRD 冲突，先报主调度，不得自行改口径。

## 2. 技术栈与架构落点（强制对齐办公系统 PRD §14）

材料模块作为办公系统的一组功能，**完全复用现有栈与目录**，不自创技术体系。开发会话开始时，先把办公系统 PRD 第 14 节作为系统提示发给开发工具（同 §14.5），确保生成代码技术栈一致。

### 2.1 技术栈（与 PRD §14.1 / §14.2 一致）

- 构建：Vite；前端框架：Vue 3 + **TypeScript**（Composition API + `<script setup lang="ts">`，禁 Vue 2 Options API）。
- 路由：Vue Router，全部懒加载（动态 import）。
- 状态：Pinia（登录用户 / 权限 / 配置全局共享，组件内不各存一份）。
- UI：Element Plus（按钮 / 表格 / 表单 / 弹窗 / 分页优先现成组件）。
- 样式：Tailwind CSS（类名写在标签上；复杂处 `<style scoped>`，不建全局 CSS）。
- 请求：axios 封装 `src/api/request.js`（baseURL + 拦截器自动带 JWT）；**所有接口请求写在 `src/api/materials.ts`，组件不直接写 axios**。
- 图表：ECharts（封装 `BaseChart.vue` 复用）。
- 后端：Node.js + Express（与现有一致）；SQLite（与现有一致，后可平滑切 PostgreSQL）。
- 鉴权：复用平台 JWT 中间件（token 前端 localStorage + axios 拦截器自动带）。
- 导出：docx / pptxgenjs / xlsx（材料模块暂不涉及，预留）。

### 2.2 目录落点（并入现有工程，不新增仓库 / 容器）

```
frontend/src/
  views/materials/        # 材料模块页面（按角色/功能分子目录）
  api/materials.ts        # 材料模块接口请求（只此一处写请求）
  types/materials.ts      # 材料实体 TypeScript 类型（响应数据全有类型，禁 any）
  store/                  # 复用现有 Pinia（追加材料模块角色态）
  router/                 # 追加 /materials/* 懒加载路由
backend/src/
  routes/materials/       # 材料模块路由（按功能分文件）
  controllers/materials/  # 控制器
  services/materials/     # 业务逻辑（编号生成、状态机、汇总、备份接入）
  models/                 # 材料模块表（软删除 deleted_at，与现有一致）
  middleware/             # 复用现有鉴权/错误处理
data/                     # SQLite 库 + 附件（材料模块数据随平台统一备份）
```
Docker：材料模块代码并入现有 frontend / backend，随现有 `docker-compose.yml` 部署，数据卷 `./data` 已含；**不新增容器**。

## 3. 协作机制（多 Agent）

- **主调度**：拆分任务、派发、跟踪、4 次不过重派、最终汇总联调。不直接写业务代码。
- **验收 agent**：按 PRD §10 执行核对（跑测试 + 实测），产出"通过 / 不通过 + 问题清单"；无权制定或修改标准。
- **执行 agent**：按任务书 + 验收标准实现，含编写并通过对应 vitest 用例，完成即消失。
- **熔断**：同一任务连续 4 次验收不通过 → 验收 agent 停止该执行 agent，报主调度重新分析（拆任务 / 修正标准 / 换方案）后派新执行 agent。
- **契约**：每阶段一份（接口 / 权限 / 数据模型 / 错误码），冲突上报不改口径。

## 7. 风险与待定

1. **平台接入细节已锁定（《接入管理 PRD》V1.0）**：模块访问权（平台层「用户-模块」关系，无权限 403）、科长审核衔接（平台返回 level≥3 且所属科室 = 计划科室，复用办公角色不另立模块审核角色）、物料账同库表关联（`material_issue_id` / `material_codes` / `material_plan_id`，合并后同 SQLite 库、非跨服务接口）、升级发版 v1.1。T8 / T10 据此实现，不再占位。
2. **技术标准一致性**：本计划 §2.3 为强制清单；每次派工把对应条目写进任务书，评审单逐条过，避免生成代码偏离办公系统栈（尤其 TypeScript 类型、软删除、统一响应、单据编号格式）。
3. **组织数据**：开工前需准备车间 / 工段 / 供应科 + 科室（领用单位）基础清单，及人员 ↔ 模块角色映射初值。
4. **工厂侧网络**：T10 部署时需实测阿里云对工厂侧的可达性（接入需求 §10）。
5. **数据库选型**：本计划按办公系统现行 SQLite 软删除约定；若平台实际为 PostgreSQL，T0 建表时同步调整，不影响任务结构。
