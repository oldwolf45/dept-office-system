## 一、演练口径

恢复必须由 **API 进程**完成，不能在容器里另起 node 脚本调服务层换文件。
原因：`backupService.swapFromZip` 通过 `closeDatabase()` / `reopenDatabase()` 在进程内换库；
若由第二个进程替换 `app.db`，运行中的 API 仍持有被删除的旧 inode，重启前的写入全部落到孤儿文件上。
所以演练脚本用 `fetch` 调 `/api/admin/*`，让恢复发生在服务进程内部。

演练用的是"备份 → 立刻恢复同一份备份"的零风险口径：恢复到备份时点，业务数据本身不变。
但库文件的确被整体替换过，可用 `backup_logs` 条数佐证——备份记录是在打 ZIP **之后**才写库的，
所以恢复后这条记录会消失。

## 三、本次演练发现并修复的问题

**备份清单记录数漏掉材料模块 13 张表**（已修，commit 6a3718a）

`RECORD_COUNT_TABLES` 只列了 v1.0 的老表，v1.1 新增的 `plans` / `purchases` / `materials` /
`material_events` / `issue_records` 等 13 张表完全不在 manifest 里。后果：恢复后的校验环节
对材料数据是否完整不闻不问，A11「恢复后校验」对材料模块等于空转。
已补齐，并新增 `backend/tests/backup-restore.test.js`（8 用例）覆盖备份/恢复/回滚/坏包拦截。
老备份包 manifest 无这些键，`swapFromZip` 按键遍历缺键跳过，向后兼容。

**容器时区是 UTC，宿主机是 CST**（已修，见下）

容器 `TZ` 未设置 → 镜像默认 UTC，宿主 CST。三个后果：

1. 所有 `datetime('now','localtime')` 写入的时间比真实时间早 8 小时，用户看到每条记录时间都是错的；
2. `maybeRunAutoBackup` 的 03:00–04:00 窗口，实际在北京时间 11 点执行（本次 03:08 UTC 即 11:08 CST 可证）；
3. `todayDate()` 取的是 UTC 日期，**凌晨 0–8 点开的采购/领用/回收/处置单据编号会用到前一天日期**。

修复：compose 两个服务注入 `TZ: ${TZ:-Asia/Shanghai}`（镜像自带 zoneinfo，无需装 tzdata）。
注意历史数据：修复前写入的行仍是 UTC 时间戳，与修复后的 CST 数据混存，
当前量级很小（11 条登录日志、8 条操作日志、20 条月报），不做批量平移。
