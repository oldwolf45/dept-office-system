## 0. 结论先行

1. **两系统是同单位不同部门的两套业务**，使用者基本不重叠，但存在一处必须打通的业务连接：**物料是材料的一部分**，办公系统「科室记账-物料账」的物料领用须与材料模块相连接。除此之外业务互不依赖。
2. **连接方式定为：合并为一个系统。** 遗留事业部办公系统（下称"办公系统"）作为平台底座，材料终生管理系统（下称"材料系统"）用办公系统的技术栈重写成一个业务模块。Python 原系统退役，不再维护。
3. **接入标准定为三件事**：账号全平台一套；平台层管"谁能进哪个模块"；角色权限归各模块自己定义。以后每接一个自建系统，都按"新增一个模块"办理。
4. **办公系统数据无损升级；材料系统测试数据弃用**，新模块从空账开始。
5. 升级完成并测试通过后，更新阿里云部署，并将新版推送至 GitHub 公开仓库。

## 2. 两者关系

1. **组织关系**：同一个单位的两个部门。事业部科室与工厂车间/供应科各管各的业务，人员基本不交叉。
2. **业务关系**：**物料是材料的一个部分。** 科室用的物料（签字笔等消耗品）属于材料体系的子集，材料模块是物料的上游——物料的采购、到货、编号、发放走材料体系的链条。因此有一处硬连接：**办公系统「科室记账-物料账」的物料领用，必须与材料模块相连接**：
   - 物料作为材料的一部分，领用事件要在材料模块留下完整记录（材料编号/批次、状态流转为"已领用"、领用单位=科室）；
   - 金额口径两边一致（物料账记的领用金额与材料模块的采购花销对得上）；
   - 材料的生命周期查询要能覆盖到发给科室的物料，链条不断。
   除物料领用外（工作管理、纯资金账等），两套业务互不依赖。科室内部的发放给个人、结存、计划销账留在物料账，不进材料模块。
3. **计划联动（已确认）**：物料账的"计划"（计划领 N 支那套）**并入材料模块的计划管理**——科室的物料需求作为需求计划报进材料模块，和车间计划一起汇总给供应科采购。物料账原有的"计划内/计划外、销账"记账流程**保留不动**：它管钱（预算口径），材料模块管料（需求与流转口径）。
4. **用户关系**：同一个人理论上可能两边都有身份（如某人既在事业部任职又参与工厂管理），按"一人一号、多模块多角色"处理，不算冲突。科室整体在材料模块中相当于一个"领用单位/计划填报单位"（与车间/工段并列）。
5. **接入动机**：管理诉求 + 业务联动诉求——把分散的自建系统收到一个平台上统一管理，同时物料的计划、领用与材料生命周期必须打通。后续还有更多自建系统接入，本次是第一例。

## 3. 连接方式：合并为一个系统

### 3.1 决策

办公系统是平台宿主，材料系统重写为其中的一个业务模块（下称"材料模块"）。合并后只有一套代码、一个数据库、一次部署、一次备份、一次升级。物料账与材料模块的联动是**同一系统内的模块间数据联动**，不是系统对接。

### 3.2 理由

1. 账号、角色权限、组织、部署运维这些高成本设施都在办公系统这边，新模块直接复用；以后每接一个系统只增加一个模块，边际成本低。
2. "接入管理"要的是管一套系统，不是管一堆系统。分系统对接意味着 N 套代码、N 个库、N 次更新，永远消不掉。
3. 数据天然互通，物料账↔材料模块的领用联动、跨模块汇总（图表、报表）在一个库内完成，不搞接口搬运。
4. 后续待接系统均为自建小型业务系统，可重写为模块，此路线可持续。

### 3.3 已否决的方案

| 方案 | 否决理由 |
|---|---|
| 统一入口 + 统一账号（分系统对接） | 部署、升级、备份的管理成本不随接入减少；数据留在孤岛里；物料领用联动要做跨系统接口，更麻烦 |
| 账号统一 + 数据互通（接口交换） | 为自建小系统维护接口层是额外负担，收益低于合并 |

**翻盘条件**：将来若接入"动不了"的系统（上级下发、成品软件），该系统走单点登录挂门户，不适用本方案的模块路线；其余自建系统仍按模块接入。

### 3.4 平台接入标准（本次起生效，后续模块沿用）

1. **账号全平台一套**：登录、工号、密码、人员信息由平台统一管，模块不再建独立账号表。
2. **平台管"模块访问权"**：谁能进哪个模块，在平台层配置。
3. **角色权限归模块**：各模块自定义自己的角色与权限点（如材料模块的工段长/车间主任/供应科），平台不把角色硬套进事业部的"副经理→科员"层级。
4. **一人多模块多角色**：按模块挂角色，互不干扰，登录后按身份进对应模块工作区。
5. **模块边界清晰**：材料模块的表、菜单、接口独立命名空间，不与办公系统现有模块混写，便于以后照此模式加新模块。模块间联动（如物料账↔材料模块）走明确的数据引用，不混表。

## 4. 材料模块的承接要求

1. 以《材料系统修正版 PRD》（第 3 步产出）为功能依据，用办公系统技术栈（Node.js + 现有前端框架）重新实现。
2. 业务流程保持不变：每月 4 日报计划 → 5 日主任审核 → 供应科汇总采购 → 25 日到货（逐件编号）→ 27 日领用 → 30 日旧料回收 → 次月 3 日处置记收入。
3. 材料状态流转保持不变：在库 → 已领用 → 已回收 → 已处置。
4. 功能模块保持修正版 PRD 界定的第一版范围：材料类别、计划、采购、到货编号、领用、回收、处置、收支分类、生命周期查询、图表汇总。
5. **物料账联动（本期必做）**：计划与领用两个环节与物料账相连接（见 2.2、2.3）：
   - **计划联动**：科室物料需求报进材料模块的计划管理，随车间计划一起汇总给供应科；填报单位扩展为"工段/科室"，科室的计划审核链在《接入管理 PRD》中定（拟：科室填报 → 科长审核 → 报供应科）。
   - **领用联动**：科室登记为材料模块的领用单位；物料账领用时关联材料编号/批次并同步状态为"已领用"；金额口径一致。
   - 物料账的"计划内/计划外、销账"记账流程保留在物料账，不迁移。
6. 复盘指出的开发过程问题（测试先行、系统化调试、验收前实测、按契约开发）不体现在产品功能里，而是作为本次重写的**开发纪律**执行。

## 5. 需求变更点（相对材料系统原 PRD）

| 原要求 | 合并后 | 说明 |
|---|---|---|
| 系统在本机运行，数据存本机，重启不丢 | 部署在平台服务器（阿里云），数据集中存储 | "数据不丢"由服务器备份保障，不再依赖本机 |
| 一键备份/恢复为本机文件 | 并入平台统一的备份体系 | 备份策略随办公系统现有机制 |
| 供应科兼管账号 | 账号归平台统一管理 | 谁建账号按办公系统现行账号规则走，材料模块内不重复建 |
| 手机端不做专门适配 | 维持不变 | 浏览器能用即可 |
| 领用单位限于车间/工段 | **新增科室为计划填报单位与领用单位** | 物料账联动要求：科室的物料计划、领用均进材料模块 |

## 6. 数据要求

1. **办公系统**：现有全部业务数据无损升级，升级后用户可继续使用，历史数据可查。这是硬要求。
2. **材料系统**：现库中只有开发测试数据，**不要迁移**，材料模块从空账开始录入。
3. Python 原系统退役后，其代码与数据文件原样保留在本地硬盘归档，不做删除（仅停止维护）。

## 7. 升级与发布路径

1. 按《接入管理 PRD》在办公系统上开发材料模块，并完成现有功能回归。
2. 测试标准：材料模块按修正版 PRD 的验收标准逐条实测；办公系统原有功能按既有验收标准回归；**物料账↔材料模块联动单独列验收项实测**；测试不允许靠删测、跳测、降标准过关。
3. 测试全部通过后：更新阿里云上运行的系统（保留数据平滑升级）→ 将新版代码推送 GitHub `oldwolf45/dept-office-system` 并发版。
4. 发布前不在任何外部渠道公开半成品。

## 9. 边界（本期不做）

1. 科室内部的物料管理（发放给个人、结存、计划销账）不进材料模块，留在办公系统物料账；材料模块与物料账只在**计划与领用**两个环节联动，不做全量数据合并。
2. 消息提醒（如每月 4 日自动催报计划）。
3. 手机端专门适配。
4. 任何新系统的接入（本期只做材料模块；新系统按第 3.4 节标准另立接入需求）。
5. Python 原系统的功能增强。

## 10. 风险与提示

1. **工厂用户访问方式**：材料模块并入阿里云部署后，工段长、车间主任、供应科需通过网络访问平台。办公系统现有网络可达性是否覆盖工厂侧，升级部署时需实测确认。
2. **组织数据初始化**：材料模块需要车间、工段、供应科的组织数据，且需把事业部科室登记为一个领用单位（物料账联动对象）。接入开发前需准备一份基础组织清单（可参照《组织数据.md》的方式整理）。
3. **角色命名冲突**：平台层新增"模块访问权"时，注意与办公系统现有按钮级权限机制的衔接，接入管理 PRD 中细化，避免两套权限打架。
